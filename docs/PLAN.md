## 한눈에 보기

결론부터: \*\*Vite + TypeScript + Three.js(셰이더)\*\*로 만들고, 별 위치는 **astronomy-engine**으로 계산한 다음 **Skyfield(파이썬)로 만든 기준값과 자동 비교**해. 배포는 **GitHub Pages**. 전체는 0\~9단계, 10단계야.

| 항목 | 확정된 내용 |
| --- | --- |
| 목적 | 그냥 해보고 싶어서 (공모전·과제 아님) |

### 이 문서 쓰는 법

1. 4장의 단계를 순서대로 해. 단계마다 "Claude Code 프롬프트"를 프로젝트 폴더에서 그대로 붙여넣으면 돼.
2. Fable이 끝났다고 하면 그 단계의 **완료 기준**을 직접 확인해. 특히 "직접 눈으로 확인" 항목은 아이폰으로 꼭 봐.
3. 다 맞으면 다음 단계로. 이상하면 그 단계 안에서 고쳐달라고 하고 넘어가지 마.

### 매 단계 공통 작업 순서

테스트 먼저 작성 → 구현 → 테스트 실행 → 화면 스크린샷 찍어서 Fable이 직접 확인 → `docs/PROGRESS.md`에 기록 → 커밋 → 너는 폰으로 확인. Fable의 강점(긴 작업 유지, 스스로 검증, 화면 확인)을 이 순서에 맞춰 쓰는 거야.

> 참고: Fable 5.2가 Claude Code 안에서 정확히 어떤 기능을 따로 갖는지는 내가 몰라. 이 계획은 Claude Code가 기본으로 하는 일(명령 실행, 테스트 돌리기, 스크린샷 이미지 읽기)만 가정했어.

## 2. 기술 스택과 고른 이유

네가 생각한 방향(Three.js + HYG + astronomy-engine + GitHub Pages)은 그대로 가고, 빈 곳만 채웠어. 바꾼 건 하나, **자동 정확도 테스트의 기준을 Stellarium에서 Skyfield로** 옮긴 거야 (이유는 표 아래).

| 역할 | 고른 것 | 이유 |
| --- | --- | --- |
| 언어 | TypeScript | 웹 그래픽은 어차피 브라우저 언어(JavaScript)로 해야 하고, 타입이 있으면 Fable이 실수를 컴파일 단계에서 스스로 잡아냄 |
| 개발 도구 | Vite | 저장하면 바로 화면 갱신, 배포용 파일을 작게 묶어줌. 설정이 거의 없음 |
| 3D 화면 | Three.js + 직접 쓴 셰이더(GLSL) | 하늘을 "안쪽에서 보는 공"으로 그리는 데 딱 맞음. 별 9,000개를 한 번에 그려서 폰에서도 빠름. 프레임워크(React 등)는 안 씁음: 화면이 거의 캔버스 하나라 필요 없고 가벼울수록 폰에 유리 |
| 별 데이터 | HYG v4.2 (6.5등급까지 잘라서 작은 파일로 변환) | 공개 데이터 중 가장 널리 쓰이고, 이름·밝기·색 정보가 다 있음. 원본은 약 12만 개라 필요한 것만 남김 |
| 별자리 선 | d3-celestial의 constellations.lines 데이터 | 88개 별자리 선이 좌표로 정리돼 있고 라이선스가 느슨함(BSD) |
| 달·행성·해, 좌표 변환 | astronomy-engine | 오차 약 ±1분(1도의 1/60) 수준, 파일 하나, 외부 서버 필요 없음. 별 좌표를 "지금 내 하늘 어디"로 바꾸는 계산도 이걸로 해서 계산 방식을 하나로 통일 |
| 은하수 | ESA Gaia 전천구 이미지를 흐릿하게 가공한 텍스처 | 실제 관측으로 만든 진짜 은하수 모양. 원본엔 별이 찍혀 있어서 우리 별과 겹치지 않게 흐리게 만듦 |
| 계산 테스트 | Vitest | "이 시각에 베텔게우스는 고도 몇 도" 같은 숫자 검사를 몇 초 만에 돌림 |
| 정확도 기준값 | Skyfield (파이썬) | 전문가들이 쓰는 정밀 천문 라이브러리. 명령어로 돌릴 수 있어서 자동 테스트용 정답지를 만들기 좋음. 파이썬은 네가 이미 쓰니까 부담 없음 |
| 화면 테스트 | Playwright | 브라우저를 자동으로 열어 스크린샷을 찍고 별을 클릭해봄. Fable이 그 스크린샷을 보고 스스로 확인하는 핵심 도구 |
| 배포 | GitHub Pages + GitHub Actions | 무료, https 기본 제공(GPS·센서에 필수), 코드 올리면 자동 배포 |
| 폰 디버깅 | 화면 안 디버그 패널 (`?debug=1`) | 아이폰 사파리의 오류를 컴퓨터에서 보려면 Mac이 필요해. Windows라서 센서 값·FPS·오류를 화면에 직접 띄우는 패널을 따로 만듦 |

**왜 Stellarium이 아니라 Skyfield를 자동 테스트 기준으로?** Stellarium은 화면이 있는 프로그램이라 설치하고 켜둔 상태에서만 값을 뽑을 수 있어. 그러면 GitHub에서 자동으로 도는 테스트에 넣기 어렵다고 판단했어(추론). 그래서 숫자 검사는 Skyfield로 자동화하고, Stellarium은 같은 시간·장소를 띄워놓고 **눈으로 비교**하는 용도로 써. Stellarium의 Remote Control 플러그인으로 비교 스크립트를 만드는 것도 가능해 보이는데, 내가 직접 확인해본 건 아니라서 9단계의 선택 과제로만 뒀어.

아래 그림은 데이터가 화면까지 가는 길이야. 별 데이터는 미리 한 번 가공해두고, 앱을 열 때마다 시간·위치로 계산해서 그려.

점선은 자동 테스트가 검사하는 곳이야. 계산(astro)을 화면과 분리해두면 그림 없이도 정확도를 검사할 수 있어.

## 3. 폴더 구조

폴더는 "계산(astro) / 그리기(render) / 입력(input) / 버튼·카드(ui)"로 나눠. 계산 코드는 화면 없이도 테스트할 수 있게 따로 두는 게 핵심이야.

```text
night-sky/
├─ CLAUDE.md              # Fable이 매번 읽는 규칙 (0단계에서 만듦)
├─ README.md
├─ ATTRIBUTION.md         # 데이터·라이브러리 출처 모음
├─ index.html
├─ package.json  vite.config.ts  tsconfig.json
├─ docs/
│  ├─ PLAN.md              # 이 계획의 요약본
│  ├─ PROGRESS.md          # 단계별 진행 기록 (Fable이 매 단계 작성)
│  └─ screenshots/         # 단계별 결과 화면
├─ public/
│  ├─ data/
│  │  ├─ stars.bin         # 가공된 별 데이터 (작은 이진 파일)
│  │  ├─ constellations.json
│  │  └─ names-ko.json     # 별자리·밝은 별 한글 이름
│  ├─ textures/milkyway.webp
│  └─ og-image.jpg         # 카톡 미리보기 이미지
├─ scripts/
│  ├─ build-stars.ts       # HYG CSV → stars.bin
│  ├─ build-constellations.ts
│  ├─ build-milkyway.ts    # Gaia 이미지 → 흐린 텍스처
│  └─ reference/
│     ├─ make_fixtures.py  # Skyfield로 정답지 만들기
│     └─ requirements.txt
├─ raw/                   # 내려받은 원본 데이터 (git에 안 올림)
├─ src/
│  ├─ main.ts
│  ├─ state.ts             # 설정, URL 파라미터(?t=&lat=&lon=&az=&alt=)
│  ├─ astro/               # 화면 없는 순수 계산
│  │  ├─ time.ts  coords.ts  stars.ts  solar-system.ts
│  ├─ render/              # Three.js
│  │  ├─ scene.ts  stars.ts  constellations.ts  moon-planets.ts
│  │  ├─ sky-color.ts  milkyway.ts  meteors.ts  aurora.ts
│  │  └─ shaders/             # *.vert, *.frag
│  ├─ input/
│  │  ├─ orientation.ts       # 폰 센서 → 카메라 방향
│  │  ├─ drag.ts  location.ts
│  └─ ui/
│     ├─ start-screen.ts  info-card.ts  settings.ts  debug-panel.ts
├─ tests/
│  ├─ unit/                # Vitest
│  ├─ fixtures/            # Skyfield 정답지 JSON
│  └─ e2e/                 # Playwright (스크린샷, 클릭 테스트)
└─ .github/workflows/
   ├─ ci.yml               # 올릴 때마다 테스트
   └─ deploy.yml           # main에 올리면 GitHub Pages 배포
```

URL 파라미터(`?t=2026-12-14T21:00+09:00&lat=37.76&lon=126.78&az=180&alt=30`)가 중요해. 시간·장소·방향을 고정할 수 있어야 Fable이 항상 같은 화면을 찍어서 비교할 수 있거든. 너도 Stellarium과 같은 조건으로 맞춰볼 때 이걸 쓰면 돼.

## 4. 단계별 계획 (0\~4단계: 뼈대와 정확한 하늘)

앞부분 0\~4단계는 "맞는 하늘"을 만드는 구간이야. 예쁜 연출은 일부러 뒤로 미뤄어. 위치가 틀린 상태에서 꼭미면 나중에 다 다시 해야 하거든.

### 0단계. 준비와 빈 사이트 배포

- **목표**: 코드를 올리면 자동으로 테스트하고 배포되는 통로를 맨 먼저 뚫기. 이게 있어야 매 단계를 아이폰으로 바로 확인할 수 있어.
- **네가 직접 할 일 (프롬프트 전에)**:
  1. Node.js LTS, Git, Python 설치 확인 (`node -v`, `git --version`, `python --version`)
  2. GitHub에서 공개(public) 저장소 `night-sky` 만들기 → 내 컴퓨터에 clone
  3. 저장소 Settings → Pages → Source를 **GitHub Actions**로 설정
  4. 그 폴더에서 Claude Code 실행, 모델을 Fable 5.2로 선택
- **끝나면 보이는 것**: `https://pkjewon.github.io/night-sky/`에 검은 화면 + "밤하늘 준비 중" 글자 + 천천히 도는 테스트용 점 몇 개
- **완료 기준**:
  - [ ] `npm run dev`로 컴퓨터에서 화면이 뜨고, `npm test`와 `npm run e2e`가 통과
  - [ ] main에 올리면 Actions가 초록불, 위 주소가 아이폰 사파리에서 열림
  - [ ] `CLAUDE.md`, `docs/PROGRESS.md`가 있음
- **확인 방법**: 자동 — CI가 테스트·빌드. 눈 — 아이폰으로 주소 열기, 링크를 나한테 카톡으로 보내서 카톡 안에서도 열리는지

```text
[0단계] "진짜 밤하늘 + 오로라" 웹 앱의 뼈대를 만들어줘.

프로젝트 설명: 실제 별 데이터(HYG v4.2)로 지금 시간·내 위치의 밤하늘을 보여주는 웹 앱. 친구들이 카톡 링크로 아이폰에서 열고, 폰을 하늘로 들면 그 방향의 별이 보인다. 컴퓨터에서는 마우스 드래그.

할 일:
1. Vite + TypeScript(strict) + Three.js 프로젝트를 이 폴더에 만들기. 프레임워크(React 등)는 쓰지 마.
2. Vitest(단위 테스트)와 Playwright(Chromium, 모바일 화면 크기 390x844 포함) 설정. 스크립트: dev, build, test, e2e, check(=tsc+test+e2e).
3. 화면: 검은 배경에 "밤하늘 준비 중" 글자와 천천히 도는 Three.js 점 몇 개. 화면 전체를 채우고 아이폰 노치/홈바 영역(safe-area)도 고려.
4. vite.config.ts의 base를 '/night-sky/'로. GitHub Actions로 ci.yml(푸시·PR마다 check)과 deploy.yml(main 푸시 시 GitHub Pages 배포, actions/deploy-pages 사용) 만들기.
5. 아래 내용으로 CLAUDE.md를 만들고, docs/PROGRESS.md, docs/PLAN.md(단계 목록만), ATTRIBUTION.md(빈 틀) 만들기.

CLAUDE.md에 넣을 규칙:
- 기술 스택 고정: Vite, TypeScript, Three.js, astronomy-engine, Vitest, Playwright. 새 라이브러리나 데이터는 추가 전에 라이선스를 확인해 ATTRIBUTION.md에 기록. GPL 라이선스 코드·데이터는 쓰지 않음.
- 작업 순서: 테스트 먼저 → 구현 → npm run check 통과 → 화면이 바뀌었으면 Playwright로 docs/screenshots/stage-N/에 스크린샷을 찍고 직접 열어서 확인 → docs/PROGRESS.md 기록 → 커밋.
- PROGRESS.md 형식: 단계, 한 일, 테스트 결과(개수·통과 여부), 스크린샷 확인 결과, 남은 문제, "사용자가 아이폰으로 확인할 것" 목록.
- 요청받은 단계 범위를 넘는 기능은 만들지 말고 PROGRESS.md의 "나중에" 목록에 적을 것.
```

### 4단계. 달·행성·해 + 시간에 따른 하늘색

- **목표**: 달(위상 포함)과 행성을 넣고, 해의 고도에 따라 낮·노을·밤 하늘색을 바꾸기. 친구들이 낮에 링크를 열 가능성이 크니까 "오늘 밤으로 보기" 버튼도 여기서.
- **끝나면 보이는 것**: 실제 모양(초승달·보름달 등)의 달, 이름 붙은 행성. 낮엔 파란 하늘에 별이 안 보이고, 해질 녕엔 주황→남색으로 바뀌며 밝은 별부터 하나씩 나타남.
- **완료 기준**:
  - [ ] 달의 빛난 비율이 Skyfield와 1%p 이내, 밝은 쪽 방향이 해 쪽을 향함
  - [ ] 낮·박명 3단계·밤 스크린샷이 각각 자연스러움
  - [ ] "오늘 밤으로 보기"를 누르면 오늘 하늘이 충분히 어두워지는 시각으로 이동
- **확인 방법**: 자동 — 정답지 비교, 달 밝은 쪽 방향 계산 테스트, 시각별 스크린샷. 눈 — 실제 달이 떠 있는 날 밖에서 모양·위치 비교

## 4. 단계별 계획 (5\~9단계: 폰, 연출, 마무리)

5단계(폰 센서)가 이 프로젝트에서 제일 까다로운 구간이야. 자동 테스트로는 절반만 확인되고, 나머지는 네가 아이폰을 들고 밖에서 확인해야 해.

### 5단계. 폰 방향 따라가기 (아이폰 우선)

- **목표**: 폰을 들면 그 방향 하늘이 보이게. 아이폰은 버튼을 눌러야 센서 허용 창이 뜨니까 시작 화면을 만들고, 안 되면 드래그 모드로 자연스럽게 넘어가기.
- **끝나면 보이는 것**: 링크를 열면 "하늘 보기 시작" 버튼 → 위치·방향 허용 → 폰을 움직이면 하늘이 따라옴. 구석에 "나침반 보정" 버튼.
- **완료 기준**:
  - [ ] 기본 자세 4가지(북쪽 수평, 동쪽 수평, 45° 위, 머리 위 천정)에서 계산된 시점이 맞음 (단위 테스트)
  - [ ] 허용 거부·센서 없음·GPS 거부에서도 멈추지 않고 드래그/서울 기준으로 동작
  - [ ] 아이폰으로 달이나 밝은 행성을 비췄서, 앱 속 위치와 실제가 대략 10° 안쪽. 보정 후엔 거의 일치
  - [ ] 손을 가만히 들고 있을 때 화면이 떨리지 않음
- **확인 방법**: 자동 — 센서 값→시점 계산 단위 테스트, Playwright가 가짜 센서 이벤트를 보내고 스크린샷. 눈 — 아이폰 사파리와 카톡 안 브라우저 둘 다, `?debug=1`로 센서 값 보면서

## 5. 어려울 것 같은 부분과 해결 방법

가장 위험한 건 폰 나침반 오차와 카톡 인앱 브라우저야. 둘 다 코드로 완전히 없앨 수는 없고, 보정 기능과 대체 경로(드래그 모드)로 버텨야 해.

| 문제 | 왜 어려운지 | 해결 방법 |
| --- | --- | --- |
| 폰 나침반 오차 | 나침반은 주변 금속·자석·전자기기에 흔들려서 수십 도씩 틀릴 수 있음(추론) | 부드럽게 따라가기, 드래그로 맞추는 "나침반 보정", 디버그 패널에 나침반 정확도 표시, "폰을 8자로 흔들어 보세요" 안내 |
| 자기 북쪽 vs 진짜 북쪽 | 나침반이 가리키는 북쪽과 별 계산의 북쪽이 다름. 한국은 약 8\~9° 차이로 알고 있는데(추론, NOAA 편각 계산기로 확인 필요), 아이폰 webkitCompassHeading이 이미 보정된 값인지는 내가 몰라 | 편각 보정을 옵션으로 만들고, 네가 밤에 달·목성을 비춰보며 켜는 게 맞는지 끄는 게 맞는지 실측해서 결정 |
| 폰을 머리 위로 들 때 | 폰이 거의 수평이면 나침반 방향이 불안정해져서 화면이 빙빙 돌 수 있음 | 회전값(쿠오터니언)으로 계산하고, 천정 근처에서는 마지막 안정적인 방위를 유지 (5단계 프롬프트에 포함) |
| 아이폰 센서 허용 | 버튼을 누른 그 순간에만 허용 창을 띄울 수 있음. 한 번 거부한 뒤 다시 묻는 방법은 정확히 몰라 | 시작 버튼 처리 함수에서 곧바로 요청. 거부하면 드래그 모드 + "사파리 탭 닫고 다시 열기" 안내, 실기에서 복구 방법 확인 |
| 카톡 인앱 브라우저 | 친구들은 대부분 카톡 안에서 바로 열 텐데, 그 안에서 센서·위치 허용이 사파리처럼 되는지는 내가 몰라 | 0단계부터 카톡으로 열어보며 확인. 막히면 드래그 모드로 동작 + "다른 브라우저로 열기" 안내 (8단계) |
| 폰 성능·발열 | 은하수·오로라 같은 셰이더는 화면 전체를 매 프레임 계산해서 무거움 | 별은 그리기 호출 1번, 후처리(블룸) 안 씁, 해상도 배율 최대 2, 느리면 자동 화질 낮추기, 탭 숨기면 멈춤 (8단계) |
| 아이폰 디버깅 | 아이폰 사파리의 개발자 도구는 Mac에서만 열림. Windows에선 폰에서 난 오류를 못 봄 | 화면 안 디버그 패널(`?debug=1`)에 센서 값·FPS·오류를 띄움. 오류가 나면 그 화면을 캡처해서 Fable에게 전달 |
| 폰으로 테스트하려면 https | 센서·GPS는 https에서만 동작해서 내 컴퓨터의 개발 서버를 폰으로 열면 안 됨 | 폰 테스트는 GitHub Pages 배포 주소에서. 급하면 임시 https 주소를 만드는 터널 도구를 쓸 수 있는데, 이건 Fable에게 방법을 물어봐 |
| 자동 스크린샷의 한계 | 테스트용 브라우저는 그래픽카드 없이 그리니까 느리고, 컴퓨터마다 픽셀이 조금씩 달라질 수 있음(추론) | "사진이 통째로 같은가" 대신 "계산한 위치가 밝은가" 같은 의미 있는 검사 위주. 통째 비교는 여유 있는 기준으로 보조만 |
| 지평선 근처 위치 | 대기가 빛을 꺾어서(굴절) 지평선 근처 별은 실제보다 약 0.5° 높게 보임 | 화면은 굴절 보정을 켜고, 정확도 테스트는 굴절 없이 비교 (1단계에 포함) |
| 낮에 링크를 열었을 때 | 진짜 하늘을 보여주면 파란 하늘만 보여서 실망스러움 | "오늘 밤으로 보기" 버튼으로 한 번에 밤으로 이동 (4단계) |
| 긴 작업 중 Fable이 방향을 잃음 | 단계가 길어지면 앞에서 정한 규칙을 잊거나 범위를 넘어갈 수 있음 | CLAUDE.md(고정 규칙) + PROGRESS.md(기록) + 단계마다 새 대화로 시작하고 "PROGRESS.md부터 읽고 시작해" 한 줄 추가 |

## 7. 배포하고 친구들한테 공유하기

배포는 0단계에서 한 번 설정하면 끝이고, 그 뒤로는 main에 올릴 때마다 `https://pkjewon.github.io/night-sky/`가 자동으로 갱신돼.

### 배포 (한 번만)

1. 저장소를 \*\*공개(public)\*\*로 만들기. 무료 계정은 공개 저장소여야 Pages를 쓸 수 있는 걸로 알고 있어.
2. Settings → Pages → Source: **GitHub Actions**.
3. main에 푸시 → Actions 탭에서 deploy가 초록불이 되면 주소에 반영 (보통 1\~2분).
4. 수정한 뒤 폰에서 예전 화면이 보이면 새로고침. 그래도 그대로면 주소 뒤에 `?v=2`를 붙여서 열어봐.

### 카톡으로 공유

1. **미리보기 확인**: 9단계가 끝나면 나에게 보내기로 링크를 보내서 사진·제목 카드가 뜨는지 확인. 카톡은 미리보기를 저장해두는 것 같아서, 이미지를 바꿨는데 예전 카드가 뜨면 Kakao Developers의 캐시 초기화 도구를 찾아봐 (이 도구가 있다는 건 알고 있지만 지금 위치는 확인 안 했어).
2. **친구들에게 보낼 문구 (예시)**:

```text
내가 만든 밤하늘 앱인데 한번 해봐 → https://pkjewon.github.io/night-sky/
① "하늘 보기 시작" 누르고 허용 2번
② 폰을 하늘 쪽으로 들면 지금 그 방향에 있는 진짜 별이 보여
③ 별 누르면 이름 나옴, 설정에서 오로라 꿈 모드 켜봐
카톡에서 움직이지 않으면 오른쪽 위 메뉴 → 다른 브라우저로 열기
```

3. **특별한 링크**: 주소 뒤에 설정을 붙여서 보낼 수 있어. 예) `?aurora=1`(오로라 켜진 상태), `?t=...`(특정 날 밤). 12월 중순엔 쌍둥이자리 유성우가 있으니까 그날 밤 링크를 보내도 좋아 (극대 날짜는 국제유성기구 IMO 달력으로 확인).
4. **개인정보**: 서버가 없고 위치는 친구 폰 안에서만 계산에 쓰여. 친구가 물어보면 그렇게 답하면 돼.

## 8. 쉬운 용어 사전

| 용어 | 쉬운 뜻 |
| --- | --- |
| 등급 (magnitude) | 별의 밝기. 숫자가 **작을수록 밝음**. 시리우스 약 -1.5, 맨눈 한계 약 6.5, 도시에선 3\~4등급까지만 보임 |
| 방위각 / 고도 | 내 하늘에서의 위치. 방위각 = 북쪽에서 오른쪽으로 몇 도, 고도 = 지평선에서 몇 도 위 |
| 적경 / 적위 | 하늘의 위도·경도. 별 목록은 이걸로 저장돼 있고, 시간·장소를 넣어 방위각·고도로 바꿔야 화면에 그릴 수 있음 |
| J2000 | "2000년 1월 1일 기준 좌표". 지구가 팔이처럼 천천히 흔들려서(세차) 기준 날짜를 정해두고 보정함 |
| 박명 | 해가 진 뒤 하늘이 완전히 어두워지기 전까지의 밝은 시간. 해가 지평선 18° 아래로 가야 진짜 밤 |
| 굴절 | 대기가 빛을 꺾어서 지평선 근처 별이 실제보다 살짝 높게 보이는 현상 |
| 자기 편각 | 나침반의 북쪽과 진짜 북쪽(북극성 방향)의 차이 |
| 색지수 (B-V) | 별 색을 나타내는 숫자. 작으면 푸른빛(뜨거운 별), 크면 붉은빛(차가운 별) |
| 셰이더 (shader) | 그래픽카드에서 돌아가는 작은 프로그램. 픽셀 수백만 개의 색을 동시에 계산해서 반짝임·오로라 같은 효과를 만듦 |
| 텍스처 | 3D 물체에 입히는 그림 파일. 은하수는 하늘 공 안쪽에 붙이는 그림 |
| 그리기 호출 (draw call) | 그래픽카드에 "이것 그려" 하고 부탁하는 횟수. 적을수록 빠름. 별 9,000개를 1번에 |
| 해상도 배율 (DPR) | 아이폰 화면은 점 하나를 픽셀 3×3으로 표현해. 이걸 2로 제한하면 계산량이 절반 가까이 줄어 |
| FPS | 1초에 화면을 몇 번 새로 그리는지. 60이면 부드러움 |
| 쿠오터니언 | 3D 회전을 표현하는 숫자 4개. 각도 3개로 표현할 때 생기는 "천정에서 빙빙 도는" 문제가 없음 |
| 단위 테스트 / e2e 테스트 | 단위 = 계산 함수 하나가 맞는지. e2e = 진짜 브라우저로 앱을 열고 클릭·스크린샷까지 |
| 정답지 (fixture) | 정밀 라이브러리로 미리 계산해둔 기준값 파일. 우리 계산을 여기에 대조 |
| CI | GitHub에 올릴 때마다 자동으로 테스트를 돌려주는 것 |
| OG 태그 | 카톡·인스타 등에 링크를 보낼 때 뜨는 사진·제목을 정하는 코드 |

## 9. 추론한 것과 모르는 것

**추론해서 정한 것** (확인해서 아니라 판단으로 정한 거야):

- 허용 오차 숫자(별·행성 0.05°, 달 0.1°, 폰 방향 10°)와 파일 크기 예산(1MB/3MB)
- Stellarium을 자동 테스트에 넣기 어렵다는 판단, 그래서 Skyfield를 기준으로 쓴 것
- 한국 자기 편각 약 8\~9°
- 데이터 ShareAlike 조건이 앱 코드까지 번지지 않는다는 해석, 한글 이름 목록의 라이선스 문제
- 자동 스크린샷이 컴퓨터마다 조금씩 다를 수 있다는 점

**모르는 것** (해당 단계에서 실제로 확인해야 해):

- Fable 5.2가 Claude Code에서 따로 갖는 기능과 사용량 한도
- 아이폰 webkitCompassHeading이 자기 북쪽 기준인지 진짜 북쪽 기준인지 → 5단계
- 카톡 인앱 브라우저에서 센서·위치 허용이 되는지 → 0단계부터
- 아이폰에서 센서 허용을 한 번 거부한 뒤 다시 켜는 정확한 방법 → 5단계
- Stellarium Remote Control API로 비교 스크립트를 만들 수 있는지 → 9단계(선택)
- Kakao 미리보기 캐시 초기화 도구의 현재 위치
